BitFSCollector ● 采集接收控制台

接收、验签、原样归档采集提交。不解压、不解析文件元数据、不去重、不建索引。

上面是按你当前访问域名自动拼出的完整提交地址（含 path），cc／cc-cli 的采集地址直接填它，不用去掉 /v1/submissions。

1 · 提交接口

方法与路径POST /v1/submissions
请求体gzip 原始字节（Content-Type: application/gzip），解压后为规范 JSON 批量记录
X-BitFSCollector-Pubkey33 字节压缩 secp256k1 公钥，小写 hex（66 字符）
X-BitFSCollector-Signaturelow-S DER 签名，小写 hex
X-BitFSCollector-SigVersion固定 1

成功（200）

{
  "version": 1,
  "archiveId": "…",
  "receivedAt": "2026-11-07T06:39:10Z",
  "pubkeyHex": "…",
  "digestHex": "…",
  "bytes": "258"
}

失败

400 / 413invalid_request：请求头、请求体非法或超限（413 不自动拆批）
401unauthorized：验签失败，不进入归档
429rate_limited：可按退避重试
500storage_failed：落盘失败，客户端不得标记成功

2 · 记录格式与签名

gzip 解压后是这样的规范 JSON（键顺序固定、无空白、按 seedHashHex 排序；服务端不解析，只验签名）：

{
  "version": 1,
  "files": [
    {
      "seedHashHex": "…64位小写hex…",
      "fileName": "example.pdf",
      "description": "",
      "fileSizeBytes": "123456",
      "mediaType": "application/pdf"
    }
  ]
}
文件身份只认 seedHashHex；长度用十进制字符串；名称、介绍变化触发重新提交，仅长度／MIME 变化不触发。

签名算法

摘要 = SHA-256("BitFSCollector/submission-v1\n" + gzip原始字节)，域前缀防止 BitFS wire 签名跨协议重放；secp256k1 ECDSA，low-S DER。私钥永远由宿主保管，SDK 只做 32 字节摘要签名。

curl 提交（gzip 与签名需先按上式备好，见第 3 节 SDK）

curl -X POST "$BASE_URL/v1/submissions" \
  -H "Content-Type: application/gzip" \
  -H "X-BitFSCollector-Pubkey: $PUBKEY_HEX" \
  -H "X-BitFSCollector-Signature: $SIG_DER_HEX" \
  -H "X-BitFSCollector-SigVersion: 1" \
  --data-binary @batch.json.gz
重试必须原样重发同一份 gzip 与签名，不要重新压缩；$BASE_URL 即本页顶部的完整提交 URL（示例已自动替换，复制即用）。只填基地址的旧配置仍然可用（自动补默认路径）。

3 · 用 SDK 签名（推荐）

Go

import collector "github.com/bsv8/BitFSCollectorProtocol/collector"

canonical, _ := collector.EncodeSubmission(records)
gzipBytes, _ := collector.GzipJSON(canonical)
sig, pub, _ := collector.SignGzip(ctx, signer, gzipBytes)
receipt, _ := collector.Submit(ctx, http.DefaultClient,
    endpoint, gzipBytes, sig, pub)

TypeScript

import * as c from "bitfs-collector-protocol";

const canonical = c.encodeSubmission(records);
const gzip = c.gzipJson(canonical);
const digest = c.digestGzip(gzip);
const { signature, pubkey } = await c.signGzip(signer, gzip);
const receipt = await c.submit(endpoint, gzip,
    signature, pubkey, digest);
TS 侧摘要已是 32 字节，签名与验签必须关闭预哈希（prehash: false），否则会被二次哈希导致验签失败。

4 · cc 配置

采集地址钱包 → 本地文件设置 → 采集上报，直接填本页顶部的完整提交 URL
启用开关同一分区；首次启用会自动补齐已有完整文件
提交状态同一分区：待提交条数、发送中、最近成功／失败
介绍编辑桶存储文件 → 编辑：改名或改介绍会触发重新提交
只上报自有导入文件；购买／下载所得不上报。队列按 Hash 合并为最新，每小时一次、超 1000 条（即 1001 条）提前提交。

5 · cc-cli 配置

~/.km/config.json 的 server.collector：

{
  "server": {
    "collector": {
      "enabled": true,
      "endpoint": "本页顶部的完整提交 URL（含 path，直接填）"
    }
  }
}

Web Admin（/api/collector/status）查看待提交数、最近成功时间与失败原因；介绍经 POST /api/collector/description {"seedHash": "…", "description": "…"} 设置。

售卖目录下多 data path 的文件全部上报；同 Hash 多路径取最小相对路径为准合并。

6 · 归档位置

每次成功提交落两个文件（日期取服务端 UTC）：

<归档根>/YYYY/MM/DD/<公钥>-<唯一编号>.gzip
<归档根>/YYYY/MM/DD/<公钥>-<唯一编号>.sig

.sig 是固定封装 {"digestHex","pubkeyHex","signatureHex","sigVersion"}，可独立核验；重试产生的新归档照常保留，不去重、不覆盖。
